# equirect 跨接縫 bbox 標註

2026-08-06

## 要解決什麼

equirectangular 影像的左右邊界(x=0 與 x=1)是同一條經線。目標走過那條線時,他的 bbox
在 x 方向是一個**跨越邊界的環狀區間**,而目前的工具沒有任何方式表達它。

實際後果不是「少一個功能」,是**每存一次檔就靜默損毀一批資料**。

## 現況調查

以 `D:\ws\detect_stream\out\gt_per_frames_0625_182214`(3840x1920,ratio 2.000)逐段統計,
`x2>1` 是上游 `gt_densify` 產出的跨縫框,`x1=0` / `x2=1` 是被削平後留下的痕跡:

| 段                       | dets  | x2>1     | x1=0 | x2=1 |
| ------------------------ | ----- | -------- | ---- | ---- |
| 000-120s(**已人工標過**) | 21057 | **0**    | 88   | 198  |
| 120-320s(未標過)         | 40041 | **4002** | 1    | 0    |

沒被工具碰過的段落保有 4002 個跨縫框(實測 `x2` 最大 1.11039);人工標過的段落一個都不剩,
只留下 286 個貼在 `x=0` / `x=1` 的截半框。

**這份數字是 2026-08-06 的快照,而且會變** —— 同日相隔數分鐘的兩次掃描,`000-020s`
2630→2634、`060-080s` 3663→3661、`100-120s` 4343→4440,標註正在進行中。任何驗收都不得
寫死這些絕對數字,只能斷言「跨縫框在 round-trip 後不變」這類與資料量無關的性質。

原因是 [gt_labeling/model.py](../../../gt_labeling/model.py) 的 `canonical_bbox`
會 `clamp` 到 `[0,1]`:上游送來 `[0.94063, y1, 1.00348, y2]`,存回去變成
`[0.94063, y1, 1.0, y2]` —— 人的尾巴不見了,而且沒有任何提示。

同一個資料集的 `labels.orig`(人工編輯前的備份)在 000-120s 段仍保有數百個跨縫框
(掃描當下 496 個),是回歸驗收的真實素材:那些框現行程式碼一存就壞。

### 下游早就支援跨縫,而且用的就是「延伸表示」

| 位置                                      | 內容                                                                          |
| ----------------------------------------- | ----------------------------------------------------------------------------- |
| `scripts/eval/eval_gt.py:17`(docstring)   | 「跨縫框可能以 x2 > 1(未 wrap 回來)表示。IoU 一律試 x 平移 {-1,0,+1} 取最大」 |
| `scripts/eval2/evaluate.py:41` `wrap_iou` | 就是上述實作;`area = clip(x2-x1, 0, None)`                                    |
| `scripts/eval2/gt_densify.py:168`         | 「不 clamp 回 [0,1]:wrap_iou 會試 x 平移 ±1,越界的預測框仍能跨縫配上」        |
| `scripts/eval2/gt_refine_crop.py:107`     | `crop_erp` 對 x 越界走環狀 wrap                                               |

所以脫隊的是 `gt_labeling`,不是別人。這次讓它歸隊,**detect_stream 一個字都不改**。

`wrap_iou` **不支援** `x2 < x1` 的寫法(會算成負寬 → 面積 0 → IoU 恆 0 → 該 GT 框永遠是
FN,靜默低估 recall),所以那條路不能走 —— 即使 `gt_refine_crop.py:150` 的註解宣稱
「跨縫時以 x2<x1 表示,同 GT 慣例」。該註解與實際資料(0 筆 `x2<x1`、4002 筆 `x2>1`)不符,
本次不修,獨立提案。

## 核心決策:把「連續表示」與「落檔表示」分開

這是整份設計的支點,其餘都是它的推論。

|          | 形式                                           | 存在於                              |
| -------- | ---------------------------------------------- | ----------------------------------- |
| 連續表示 | `x1 < x2`,x1 為任意實數,寬 `w = x2-x1 ∈ (0,1]` | 記憶體中的 `det.bbox`、畫布所有運算 |
| 落檔表示 | `x1 ∈ [0,1)`,`x2 = x1 + w`(可 > 1)             | JSON                                |

轉換只發生在 `canonical_bbox`,也就是存檔那一刻。**載入時不需要轉換**,因為落檔表示本身
就是一個合法的連續表示(`0.94063 < 1.00348`)。

這個閉環的價值:拖曳、縮放、hit-test、內插全都是普通矩形運算,**沒有任何環繞特例**。
跨縫不是靠 `x1 > x2` 表達的,是靠 `x2` 越界表達的,所以 `canonical_bbox` 照樣可以 sort x,
反向拖曳(拖到起點左邊)仍然正確。

JSON schema 完全不動:仍是四個 float、欄位與 key 順序原樣、存檔契約前三條不變。變的只有
第四條對 x 值域的約定。

## 1. 座標契約(`model.py`)

`canonical_bbox(bbox, wrap: bool = False)`。`wrap=False` 時行為與現在**逐位元相同**,
非 equirect 資料完全不受影響。

`wrap=True` 時 y 軸不變(sort → clamp `[0,1]` → round 5 → ensure span),x 軸改成:

```
sort(x1, x2)
w = x2 - x1
w = min(w, 1.0)              # 超過一整圈沒有意義
w = max(w, MIN_SPAN)         # ensure span:wrap 下沒有 1.0 上限,直接往右長
x1 = round(x1 % 1.0, 5)
x2 = round(x1 + w, 5)
```

- **不 clamp x**:越界是跨縫的表達方式,夾掉就是現在這個 bug。
- **仍 sort x**:跨縫由 `x2` 越界表達,不由 `x1 > x2` 表達,所以 sort 不會吃掉資訊,
  反而保住「反向拖曳」的既有行為。
- **w 夾到 1.0**:超過一整圈的框沒有物理意義,且會讓下游 IoU 退化。
- **`_ensure_span` 的 x 分支簡化**:wrap 下 x 沒有 1.0 上限,零寬時直接 `x2 = x1 + MIN_SPAN`,
  不需要現行的「頂到 1.0 就往左長」fallback。y 分支不動。
- **Python 的 `%` 對負數回正值**,所以往左出界(`x1 = -0.03`)自然收斂成 `0.97`,不需特判。

三個必須成立的性質:

1. **非跨縫框輸出不變**:`[0.3, 0.4]` → `w=0.1` → `0.3 % 1 = 0.3` → `[0.3, 0.4]`。
   「dets 沒改就 byte 相同」的契約因此保住。
2. **冪等**:`[0.94063, 1.00348]` 存回去仍是自己;重開再存還是自己。`x2` 由 round 後的
   `x1` 重算再 round 一次,二次存檔的浮點誤差在 5 位小數下必然收斂。
3. **開檔即乾淨**:上游的 `x2=1.00348` 讀進來、canonical 後仍是自己,不會一開檔就被標成
   已改動。

`Det.to_json(wrap: bool)`,由 `FrameLabel.dets_json()` 依 `FrameLabel.wrap_x` 傳入。

存檔契約第 4 條改寫為:

> `bbox` 一律寫成 5 位小數、保證非零寬高。y 一律 clamp 到 `[0,1]`;x 在環景模式下**不**
> clamp,以 `x1 ∈ [0,1)` + `x2 = x1 + w` 落檔,`x2` 可越界 —— 這是上游 `gt_densify` 產出、
> 下游 `wrap_iou` 消費的既有表示,不是本工具發明的。非環景模式下 x 維持 clamp 到 `[0,1]`。

## 2. 環景畫布(`transform.py` + `canvas.py`)

`ViewTransform` 新增 `wrap_x: bool`:

- `clamp_offset`:wrap 時 x 改成 `off_x %= span_x`(不再夾住),y 邏輯完全不動。
  取模同時擋掉長時間平移的浮點漂移。
- 新增 `visible_shifts(view_w) -> range`:算出哪幾個整數圈 `k` 使
  `image_rect + k*span_x` 與視窗相交。**這是環繞語意的唯一入口**,繪製與 hit-test 都經由它,
  維持「座標換算只有一處」的既有不變量。

`canvas.py` 三處對每個 `k` 重跑,其餘不動:

- `_draw_image`:影像左右重複鋪排。wrap 時不畫左右垂直邊界線(邊界不存在了),改在 `x=0`
  畫一條淡色接縫參考線,讓人知道 JSON 的 0/1 落在哪。上下邊界線照畫。
- `_draw_dets` / `_draw_new_box`:框與標籤在每份上各畫一次,人在接縫任一側都看得到 id。
- `_hit_box` / `_hit_handle`:對每個 `k` 平移後測試。

x 方向的 `[0,1]` 夾限在 wrap 時拿掉三處:

- `_apply_move`:x 位移不夾(y 仍夾)。
- `_apply_resize`:x 不夾,改為限制 `w < 1` 圈(y 仍夾)。
- `_clamp01`(新框起點與拖曳中的終點):x 不夾(y 仍夾)。

**y 方向全部維持原樣** —— equirect 的上下是極點,不是環狀鄰接,越過去取到的是另一側的
天空/地面。這與 `gt_refine_crop.crop_erp` 的判斷一致。

## 3. 內插走最短弧(`model.py`)

`interpolate_missing` 目前逐座標線性內插。wrap 下錨點 A `x1=0.97`、錨點 B `x1=0.02`
會內插出一串橫掃整張圖的假框。

修正:內插前先把 B 的 x1/x2 整體平移 `round(cx_A - cx_B)` 圈,使兩者相鄰,再照常線性內插,
結果交給 `canonical_bbox(wrap=True)` 收回 `[0,1)`。作法與 `gt_densify.interp_box` 一致
(該處註解:「x 走 ERP 最短弧,跨縫時不會橫掃整張圖」)。

`plan_remap` / `plan_track_delete` / `find_track` 只動 `track_id`,不碰 bbox,不受影響。

## 4. 啟用判定與 UI(`window.py`)

- `FrameLabel.is_equirect`:`size[0] == size[1] * 2`。三個現有資料集皆為 3840x1920,命中。
- `FrameLabel.wrap_x`:執行期欄位(**不是** JSON 欄位),由 window 在載入後統一設定。
- 檢視選單新增可勾選的「環景模式(ERP)」:開檔時依 2:1 自動勾上,可手動覆寫,切換時
  更新所有 `FrameLabel.wrap_x` 與 `canvas` 狀態。
- **不給快捷鍵**:它改變的是存檔語意,誤按的代價比省一次點擊高。
- 狀態列顯示目前是否為環景模式。

非 2:1 的資料自動維持現行行為(clamp 到 `[0,1]`),不會讓人在 perspective 影像上畫出
`x2>1` 的框 —— 那種框 `wrap_iou` 的 ±1 平移不會命中,會靜默算錯。

## 5. 貼邊警示(`model.py` + `panel.py`)

`FrameLabel.has_edge_box`:`wrap_x and any(x1 == 0.0 or x2 == 1.0 for ...)`。

- **模式判斷寫在 property 裡**,不由 `panel` 自己再判一次 —— 與 `has_duplicate_track` 等
  既有 property 同一風格,呼叫端只問「要不要亮」。非 equirect 資料貼邊是正常的,恆回 False。
- **精確相等比較是刻意的**:clamp 產生的正是這兩個值,而 canonical 後所有座標都是 round
  到 5 位的十進位值,不存在「差一點點」的情況。
- `x2 > 1` 是健康的跨縫框,**不**警示。

幀清單旗標加 `CUT`,顏色優先序 `DUP > CUT > 待補`(重疊是已經填錯、貼邊是可能被削過、
待補是還沒填);摘要加一行「貼邊 N 幀」。

這同時是回溯手段(找出 000-120s 那 286 個被削平的框,人工在環景畫布上把尾巴拉回來)與
往後的防呆(任何原因造成的貼邊都會被看見)。

## 不做的事

- **不改 detect_stream 任何檔案**,含 `gt_refine_crop.py:150` 那行與實際資料不符的註解。
- **不自動回溯修復** 000-120s 那 286 個框。`labels.orig` 是人工編輯前的版本,若該框位置或
  大小已被人工調整過,從它補回來的尾巴長度就是舊值 —— 交給 `CUT` 警示人工處理。
- **不動 y 軸任何行為**。
- **不動** track_id / ppe / 換號 / 刪軌跡 / band 相關邏輯。
- **不新增 JSON 欄位**,不引入設定檔。

## 風險與已知取捨

- **手動關掉環景模式後存檔,會把跨縫框 clamp 掉。**(原判斷,執行中被推翻,見下。)
  最初認為這是使用者明示的操作,不必額外攔阻,狀態列一直顯示目前模式就夠了。
  Task 6 執行時 human partner 指出這個判斷站不住:autosave 預設開啟,「取消勾選
  環景模式 → 翻一幀」就會在使用者完全沒有存檔意圖的情況下,把整份資料集的跨縫框
  依 `[0,1]` clamp 靜默寫回磁碟——那是關掉一個勾選方塊的**副作用**,不是「明示的
  操作」;而且 `wrap_x` 不進 undo stack、也不是 JSON 欄位,重啟後同樣救不回來,
  狀態列那行字不構成有效的警示。裁決是加一道確認對話框:`window.py` 的
  `_confirm_leave_wrap`,只在「關閉環景」且確實有框的 canonical 結果會因模式而不同
  (存出去會不同)時才彈,預設停在「否」。進環景的方向不受影響,那個方向不會損失資料。
- **`w > 1` 的框被夾成一整圈。** 實務上人不會畫出這種框;夾掉比讓它繞多圈後在下游變成
  無意義的 IoU 好。
- **驗收 #8 依賴 detect_stream 的路徑存在。** 找不到就跳過該項並印出原因,不讓
  gt_labeling 的測試硬綁另一個 repo 的位置。
- **README 的存檔契約段落必須同步更新**,它是本工具的驗收依據。
